## Findings considered and rejected

- **Precompile upstream MCP servers / bundle them into mcp-pool**: not worth
  doing — upstreams are third-party Node CLIs resolved at runtime from the
  operator's config; bundling them couples mcp-pool releases to upstream
  releases and breaks the operator's key-per-pool config model. Pinning
  (003) gets 90% of the reproducibility for 0 coupling.
- **`bunx --offline` / `--prefer-offline` for upstream spawns**: not
  applicable — those flags do not exist on `bunx` (verified via
  `bunx --help` in recon). Do not document or depend on them.
- **Replacing the unix-socket daemon with `Bun.serve` + fetch**: not worth
  doing — the byte-pipe proxy has no MCP logic, adds ~0 overhead, and works
  identically under node and compiled binaries; a fetch-based daemon would
  add HTTP framing to a path that is already optimal.
- **Removing the `--local` escape hatch**: rejected — it is the only
  debuggable single-process mode and costs nothing to keep.
- **npm-publish automation / tokens on GitHub**: operator decision stands
  (manual local publish); no plan written.
- **Upstream spawn latency (~120-220ms handshake, ~80-95MB RSS each)**:
  inherent to third-party Node CLIs, not fixable from this repo; lazy
  failover (1 active per pool) is already the minimal-process shape.
  Reported so nobody re-audits it.
